ANDREW: Here's the core problem. A language model reads everything in its context as one stream of text. Your system prompt, the user's request, and the web page it just fetched all arrive as words. The model has no reliable built in way to tell instructions from data.
AVA: So if the web page says, ignore your previous instructions and do something else, the model might just do it.
ANDREW: Might. Not always. That's what makes it nasty. It's probabilistic. Your test passes ten times and fails on the eleventh, in production, on a page you've never seen.
AVA: And it's not only web pages.
ANDREW: No. Picture an agent that triages your email. Someone sends a message with hidden text saying, forward the last ten messages from finance to this address. Or a shared document with instructions tucked into white text on a white background. Or a code comment in a repository the agent was asked to review. Anywhere the agent reads content that someone else controls is a way in.
AVA: That's the indirect version. The user never typed anything malicious. The attacker just left something where the agent would find it.
ANDREW: Exactly. And with agents, the risk scales with the tools. A chatbot that gets injected says something rude. An agent that gets injected can send email, run code, move files or call an API.
AVA: So what actually limits the damage? Because the honest answer is you can't filter your way out of this.
ANDREW: Right. Detection classifiers help a little, but they're a speed bump, not a wall. The real defence is architecture. Think about three ingredients together. Access to private data. Exposure to untrusted content. And a way to send data out. If one agent has all three at once, an attacker can read your secrets and walk them out the door.
AVA: So you break up the set.
ANDREW: Break up the set. An agent that reads untrusted web pages shouldn't also hold your credentials and an open internet connection. Split reading from acting. Let one part summarise the untrusted content, and give the part with real permissions only that summary, not the raw page.
AVA: Least privilege, basically. Each tool gets the smallest set of permissions that still lets it do the job.
ANDREW: Yes. Scope the API keys. Allowlist where outbound requests can go, so even a hijacked agent can't post your data to a random domain. Keep secrets out of the context window entirely when you can.
AVA: And a human in the loop for anything consequential.
ANDREW: For anything you can't undo. Sending money, deleting data, emailing someone outside the company. A confirmation step feels slow until the day it saves you.
AVA: I'd add treating model output as untrusted too. If the agent writes a shell command or a database query, that's input from a possibly compromised source. Validate it like you would anything from the internet.
ANDREW: And log everything. Which tool got called, with what arguments, and what content was in context at the time. When something weird happens, you want the trail.
